# 单实例备份与恢复（F09a）

适用于当前 Node.js 22.13+、SQLite 单实例。命令由有数据库文件权限的部署人员本地运行，不提供 Web 远程执行入口。先 `npm ci`、`npm run build`。本阶段完成隔离恢复演练，未部署真实 MedicalCareWeb 环境。

## 创建备份

```powershell
npm run db:snapshot -- backup data/health.sqlite data/backup-20260908
```

源文件须存在，目标目录的父目录须存在，目标目录必须全新。采用参数化 `VACUUM INTO` 生成含 WAL 已提交数据的一致性快照，不直接复制在线数据库主文件。备份读取源库而不更新业务内容。机制依据 [SQLite 官方备份说明](https://www2.sqlite.org/backup.html)。

成功目录包含 `state.sqlite` 和最后写入的 `manifest.json`（版本、UTC 时间、SHA-256、各表数量、是否清除会话）。源库与输出都执行 integrity_check，并确认当前七张业务表可查询；输出文件和清单调用 fsync。成功以退出码 0 和 verified 标识判定，不能仅以文件存在判定。磁盘不足、锁冲突或中断失败时保留残留目录便于检查，换新目录重试，不复用失败目录。大型数据的耗时、锁等待和磁盘空间应在实际部署容量下测量，本工具无总执行超时保证。

备份包含服务、探测、告警规则/事件、维护、审计及加密会话，须按敏感运维数据保护。父目录由部署人员预先设置仅服务/备份账户可读写的权限；POSIX 新目录权限为 0700，Windows 必须单独配置 ACL。备份不包含授权文件、密钥、TLS 配置或应用版本，需分别管理和记录对应版本；不得提交真实备份到 Git。示例使用已忽略的 data/。校验值用于检测意外损坏，不是签名或防篡改证明。

## 隔离恢复与切换

```powershell
npm run db:snapshot -- restore data/backup-20260908 data/restore-20260908
```

恢复先检查清单版本及 SHA-256，然后在全新目录生成并检查数据库。备份目录应只读、静态，不得指向正在运行的数据库目录，也不得在恢复过程中修改文件。工具不覆盖现有文件、不自动启动服务。恢复副本删除旧平台会话并写入 database.restored 系统审计，用户需重新登录；原始备份和运行库不变。该系统审计无环境归属，目前不会出现在环境审计页面。

1. 隔离演练使用测试授权文件及本机白名单目标，核对服务、探测、告警、维护和审计数量及内容。不要把生产探测配置直接用于演练启动。
2. 计划正式切换前，停止原后端、入口写流量及相关调度，保留原库、WAL/SHM 和应用/配置版本，重新评估最新备份时间与允许丢失窗口。
3. 将 STATE_DB_PATH 指向新目录下 state.sqlite，注入受控授权文件、身份 URL、PLATFORM_ORIGIN 和 SESSION_KEY。恢复副本没有旧会话，但服务仍要求有效密钥配置。
4. 使用匹配代码版本启动；验证 /health/live、/health/ready、重新登录、环境权限和关键业务数据。ready 仅覆盖平台依赖，不代替目标监控验收。
5. 核对 running 探测的中断恢复和冷却行为，确认正常采集后恢复入口流量。恢复会使备份之后的数据缺失；不得默认为零数据损失。
6. 回退时再次停服务，将数据库路径和代码/配置一同切回保留版本。不要把旧主文件覆盖到带有新 WAL 的目录。回退后产生的数据分歧需单独处理，不自动合并。

正式部署仍需 TLS 入口、服务托管、权限 ACL、监控、容量、备份保留及异地保存策略验收。当前不自动安排备份或清理，RPO/RTO 尚未承诺。
